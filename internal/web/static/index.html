The problem

10:00 AM. Everyone clicks “Book”. Then something breaks.

A server gets slow

It still answers health checks, so a normal load balancer keeps sending it a third of the traffic. Every one of those users waits seconds.

A server crashes

Requests keep failing until the next health checks notice. At 2,000 requests a second, that's thousands of failed bookings.

Traffic beats capacity

Queues explode and everyone slows down: the person paying for a ticket as much as the person browsing offers.

How a request flows

Six steps. Every request. In about a millisecond.

Self-healing

It fixes itself. Then it tells you why.

⇄

Smart routing

Power-of-two-choices over live latency (P2C-EWMA), the idea behind Linkerd and Twitter's Finagle. A slow server drops to ~1% of traffic within a second.

⏏

Instant ejection

5 failures in a row and the server is out, in milliseconds instead of seconds. Never more than half the fleet.

↗

Slow start

A recovered server earns its traffic back over 8 seconds instead of being flooded and falling over again.

↻

Smart retries

Failed reads are retried elsewhere, capped at ~20% extra load so retries can never snowball into a storm.

⚑

Priority shedding

When latency passes the target, browsing is turned away first. Bookings and payments keep flowing.

＋

Autoscale

Dead servers are replaced and extra ones launched during the rush, then drained and retired when it ends.
